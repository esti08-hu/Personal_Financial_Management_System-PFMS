
# Workspace Instructions (PFMS)

Follow these rules when proposing or implementing changes in this repo.

## General
- Prefer small, reviewable changes; avoid large refactors unless requested.
- Match existing patterns and naming conventions in the touched area.
- Keep code TypeScript-first and strongly typed; avoid `any`/`unknown` unless justified.
- Do not introduce new libraries unless there is a clear need and the repo already uses them.

## Frontend (Next.js in `client/`)
- Keep each component under **600 lines** and maintain a modular file structure.
- Prefer composition: split large UI into smaller components + hooks in `client/hooks/`.
- Reuse existing design-system/UI components; do not invent new visual primitives without asking.
- Keep client/server boundaries clear (App Router): avoid importing server-only code into client components.

## Backend (NestJS in `server/`)
- Use NestJS module/service/controller patterns; keep business logic in services.
- Validate inputs with DTOs and `class-validator`/`class-transformer`; fail fast with clear errors.
- Keep API contracts explicit and consistent; update Swagger decorators when endpoints change.
- Avoid leaking secrets or sensitive user data in logs or error messages.

## Database (Drizzle + Postgres)
- Any schema change must include a migration under `server/drizzle/`.
- Prefer additive/backward-compatible migrations; be cautious with destructive changes.

## Testing & Quality
- If behavior changes, update/add tests close to the change.
- Backend: Jest unit/integration tests where applicable.
- Frontend: Jest for components/logic; Playwright for critical user flows when relevant.
- Keep tests deterministic (no real network calls; mock external AI/providers).

## Tooling
- Use `pnpm` (not `npm`/`yarn`) for workspace commands.
- Keep Docker-related changes compatible with `docker-compose.yml` workflows.
